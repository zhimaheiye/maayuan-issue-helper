# 输出约定

## forum-post.txt：可直接复制到 QQ 频道

纯文本，无需表格或附件也能理解。下面是字段结构，不是虚构的示例事实：

```text
【问题反馈】功能名 + 实际异常
发生时间：日期、时间范围、时区（未知就注明）
环境：系统、模拟器、游戏区服/语言、资源/GUI/框架版本（有证据才填）
操作：用户实际做的步骤
预期：用户希望发生什么
实际：画面和行为；是否每次发生
日志事实：1–3 条相关事实，带相对文件名和 L 原始行号
初步判断：可能原因或尚无法确定，明确为 AI 辅助判断
已尝试：真实操作及结果；没有则写未尝试
附件：本地日志包文件名；未上传。或用户已提供的链接及有效期
待补充：真正影响定位的信息
```

没有复现确认不能写“必现”，没有验证不能写“已修复”。不要把“最新版”当版本号。不为用户分配严重度、开发者或截止时间。一般 300–600 字，确有关键证据时可适当增加。

## report.md：开发者可复核的长报告

1. 标题、报告 ID、采集时间与故障时间（分开）、用户陈述。
2. 版本与环境：每项附来源；无法确认的字段集中列出。
3. 操作步骤、预期与实际、复现频率；截图说明只陈述看见的内容。
4. 故障时间线：起点、最后正常节点、异常、结束状态；日志文件及原始行号。
5. 关键日志摘录：保留上下文、时间和节点/任务 ID，避免整页堆日志。
6. 已确认事实、可能原因、反证/缺失证据、建议的下一次观察。单纯关键词匹配不足以确诊。
7. 已尝试操作及结果；有本地修复时注明副本、文件改动、验证范围、回退与更新注意事项。
8. 附件范围：脱敏方式、排除内容、截断/缺失/变化、是否对应本次故障。

长报告通常 1–3 屏即可。AI 的价值在于压缩和关联证据，报告更长不等于更有用。

## 交付

同一个反馈同时提供短文、长文、日志包，不强制使用者开 GitHub 账号。先复核正文与附件再发布。若用户选择 GitHub，可把长报告粘贴到项目当前模板并附包；只有用户明确要求提交时才执行外部提交。网络不可用不妨碍本地生成。
