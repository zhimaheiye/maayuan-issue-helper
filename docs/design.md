# 设计依据与范围

调查日期：2026-10-26。

## 要解决的问题

使用者往往能描述“卡住了”并截图，但不知道需要哪类日志、对应哪个运行时段和版本。本技能把这些材料转为短反馈、可复核的详细说明和可携带的证据包，让后来看到反馈的人也能继续排查。

报告应脱离某个个人的在线状态成立，不指定作者接收反馈，不替官方承诺处理。默认收集与分析；使用者明确要求后才在副本中尝试修复。更新兼容性不能通过一次本地修复保证。

## 参考项目

这次搜索找到了相近方案；没有据此断言“没有任何同类技能”。以下作为设计参照，没有直接复制其实现：

- [Kepsilent/Bug-Report-Skill](https://github.com/Kepsilent/Bug-Report-Skill)：通用日志分析与结构化 Bug 报告技能，配套应用日志接入。本技能面向已经下载 MaaYuan 的终端使用者，直接读取现成日志，不要求在项目中接入 SDK。
- [obra/superpowers systematic-debugging](https://github.com/obra/superpowers/blob/main/skills/systematic-debugging/SKILL.md)：强调先调查根因再修复，面向开发排障。本技能着重整理可移交的证据，证据不足时保留不确定性。
- [replicatedhq/troubleshoot](https://github.com/replicatedhq/troubleshoot)：诊断材料的收集、脱敏与分析框架，主要面向 Kubernetes。可借鉴采集清单和诊断包分离的思路，不是 MaaYuan 即插即用技能。

## MaaYuan 现有公开流程所能确认的部分

[MaaYuan Issues](https://github.com/syoius/MaaYuan/issues) 已有用户反馈入口。[Issue #373](https://github.com/syoius/MaaYuan/issues/373) 中用户提供了 ZIP，维护者从日志提出 Agent 初始化方向，并要求补充启动环节记录。这说明 GUI、框架和 Agent 日志关联具有实际价值。

检查默认分支 `v5` 的 `.github` 时，仅看到了 `workflows`，未发现 `ISSUE_TEMPLATE`。这只是当次检查结果，不能推断项目没有其他反馈规范，更不能推断维护者的日常排期、频道管理或响应承诺。

## 本地观察

桌面发行目录可同时存在 GUI 日志、框架当前/轮转日志、Python Agent 日志和错误截图。文件夹名的发行版本可能落后于原地更新后的资源版本，所以报告从配置与运行记录分别取证。

仓库不包含观察到的个人日志、账号配置或截图；测试只使用合成样本。

## 实现取舍

- `SKILL.md` 不绑定某一家专用工具；Python 采集器无第三方依赖。
- 三类产物共用一份证据，先完成报告再打包，避免 ZIP 内仍是旧草稿。
- 采集上限防止大型日志拖垮工具，所有截断都有记录；默认包不声称完整。
- 规则脱敏是辅助，不保证所有语义隐私已去除。截图默认排除，以免把账号画面直接分享。
- 本版按日期筛选，多行堆栈继承上一时间戳的日期。跨日分别采集；更精细时段由 AI 根据行号分析。非标准日志文件名可能需要人工定位。
- 不因文件夹已备份就默认可以重跑游戏操作；程序副本不隔离真实游戏账号或共享模拟器。

## 发布与后续验证

Windows + Python 3.12 的脚本测试覆盖日期筛选、堆栈上下文、常见脱敏、中文路径、UTF-16/GB18030、截断、链接排除、打包路径限制和校验值。宿主导入入口依官方文档整理，尚需在 WorkBuddy、Qoder 的具体版本中分别试装。Mac/Linux 的路径逻辑可用标准库运行，但未做实际机器验收；Android 日志布局未适配。
